# W1-B · Face service — handoff (wave 1)

## Summary
The Space half of F2 is done in `face-api/main.py`: when `FACE_API_KEY` is set, `POST /extract` answers `401 {"error":"unauthorised"}` unless `x-face-key` matches (constant-time `hmac.compare_digest`, checked in an ASGI middleware before the multipart body is parsed, body drained so the HF proxy delivers the 401 cleanly); `/`, `/health` and the new warm ping stay open; with the variable unset every response is byte-for-byte what it was. `GET /extract` **and** `HEAD /extract` now both return 200 in ~2 ms with no body read and no inference (the old service answered both with 405 — FastAPI does not add HEAD to GET routes, so the route lists both methods). Two things the brief asked to *confirm* turned out to need code: inference ran inside an `async def` handler and blocked the event loop (on the live Space today, `HEAD /extract` took 15 s / 8 s / 9 s and once timed out at 30 s while something was being extracted — `docs/audit/handoff/shots/W1-B/live-space-observations.txt`), so `/extract`'s CPU work now runs in worker threads behind an `anyio.CapacityLimiter` (`FACE_MAX_INFERENCE`, default 2): three or six concurrent calls all succeed, `/health` answers in 3–8 ms under load, and calls beyond the cap queue in order. Startup also warms every loaded model and the face-alignment path once, because the first face photo in a fresh process cost 9.06 s locally (0.55–0.60 s afterwards). A tiny-image guard was added to the HOG step (OpenCV asserted → 500 for frames under 64×128; now `appearance: null`). `requirements.txt` and `Dockerfile` are unchanged. Verified with a new pytest file (8 tests, all pass in a Python 3.10 venv), curl against uvicorn on port 7861 with the model stubbed, and — despite no compiler on this Mac — with the real buffalo_l detection + recognition models loaded from a mirror through the insightface source tree; transcripts are in `docs/audit/handoff/shots/W1-B/`. Cold start of the *live container* could not be observed (no restart allowed, no HF token here); local numbers and a labelled estimate are below. `npm run check` (exit 0) and `npm test` (99/99) pass at the end of the run.

## Concurrency answer for W3-B
Three concurrent `/extract` calls **work**: none fail, none are rejected, and the event loop stays free (the warm ping, `/health` and the Worker's 3 s deep probe answer in milliseconds during inference — they did not before). With the default `FACE_MAX_INFERENCE=2` two calls run in parallel threads and the third waits in-process; with 3 all run at once. Honest caveat on throughput: onnxruntime already uses every core for one inference, so parallel calls did **not** raise throughput on the M1 (3 × 6-face photos: 1.71–2.35 s concurrent vs ≈ 1.7 s sequential; surf photo 0.75 s vs 0.67 s) — expect the same on the Space's 2 vCPU: per-call latency under 3-way load ≈ 2–3× solo, total work the same. Raising the queue consumer to `max_concurrency: 3` is therefore **safe** (a queued third call waits well inside the Worker's 75 s fetch timeout, and the response never fails) and it does buy overlap of the Worker's R2 read + upload + network time with inference, but it will not triple indexing speed by itself. Guest `/api/match` calls share the same slots, so a long re-index slows guest searches; keep `FACE_MAX_INFERENCE` at 2 on the 2 vCPU Space (raise only with more vCPUs). Memory: threads share the one loaded model (RSS ~530–600 MB after warm-up, no growth per slot); multiple uvicorn workers would each load the model and each re-download it on a cold start — that is why the `Dockerfile` CMD is unchanged. Local numbers are a lower bound: the Space runs the full 5-model pack (landmark + gender/age models per face, absent locally) on 2 vCPU x86.

## Cold start (what was measured where)
- **Live Space (cpu-basic, 2 vCPU / 16 GB, Docker SDK, 1 replica, `gcTimeout` 172800 s = sleeps after 48 h idle):** a fresh container happens on every push/rebuild, every secret change, every restart and every wake-up. The image does **not** contain the model (commit a13d85e removed the build-time pre-download one commit *before* d8d7253 added the compiler that had made that step fail), so every fresh container downloads `buffalo_l.zip` (275 MB) from GitHub releases, unzips it, builds five onnxruntime sessions and only then starts listening — until then the Space proxy answers, `/health` is unreachable, and `model_loaded:false` never shows. The container's own cold start could **not** be observed from this machine: the Space stayed RUNNING all session (agents must not deploy/restart it; run logs need an HF token and none is stored here — `~/.cache/huggingface/token` absent). Live `/health` today: 0.86–3.8 s per call from this network (floor ≈ 0.9 s proxy round trip), with 2–4 s outliers consistent with the blocked event loop.
- **Local (M1, Python 3.10, same pins, models pre-placed so no download):** process start → first `/health` 200 = **5.96 s** on a cold file cache (model/session build 3.8 s, imports ≈ 1.3 s, warm-up 0.1 s) and **1.6–1.7 s** on later starts (load 0.4–0.6 s, full warm-up 0.6 s). First face photo after start: 9.06 s before the full warm-up (first ArcFace run + scikit-image's lazy `transform` import), 0.6 s after it.
- **Estimate for the Space (labelled estimate):** download 275 MB inside HF's datacentre ~10–20 s + unzip ~2 s + five session builds on 2 vCPU (2–4× the M1's 3.8 s → ~8–15 s) + warm-up (a few seconds; the recognition warm-up is now paid here instead of on the first guest) + uvicorn ≈ **25–45 s** from container start to first `/health`, on top of HF's own scheduling (tens of seconds on a wake-up; minutes for a rebuild, because `pip install insightface` compiles a C++ extension — that layer is cached as long as `requirements.txt`/`Dockerfile` do not change, and they did not). The new startup line `Face model ready: load Xs, warm-up Ys, …` in the Space logs gives the real number after the first deploy — please record it in the runbook.
- **Follow-up worth doing (not done; Dockerfile deliberately unchanged this wave):** re-add the build-time pre-download (`RUN python -c "from insightface.app import FaceAnalysis; FaceAnalysis(name='buffalo_l')"`) now that `build-essential`/`g++` are in the image — it removes the 275 MB download from every cold start at the cost of a ~300 MB larger image. It was dropped in a13d85e because the build failed before the compiler existed, not because baking the model was wrong.

3. `npm run deploy:api` with W1-A's Worker change that sends `x-face-key`. The Space ignores the header until step 4, so 2 and 3 can be in either order, but the Worker must be sending it **before** step 4.
4. Space → Settings → Variables and secrets → add secret `FACE_API_KEY` with the same value (the container restarts: cold start applies). Verify `GET /health` → `"key_required":true`; `curl -X POST …/extract -F file=@photo.jpg` → `401 {"error":"unauthorised"}`; same with `-H "x-face-key: <value>"` → 200; Worker `GET /api/health?deep=1` → `face: ok`; then one crew re-index of a small session.
Optional Space variable: `FACE_MAX_INFERENCE` (default 2; leave it on cpu-basic). Rollback: delete the Space secret (container restarts, check is off) — the Worker's extra header is harmless. Key rotation = steps 2–4 with a new value, Worker first.
