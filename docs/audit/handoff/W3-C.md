## Summary

- **Bulk select in the photo grid** (`viewSessionPhotos` + the "Photo grid: bulk select" block in `admin.js`): a 44 px checkbox per tile (always visible on touch, hover/focus/selection-revealed on pointer devices), "Select all" / "Clear", a footer action bar with the live count ("3 selected") and Re-index · Set cover · Move to… · Delete. Delete is a typed confirm (`DELETE`, reusing `confirmAction`), Re-index a plain confirm, Move a pick list of the other non-archived sessions (new `choice` slot in the confirm dialog), Set cover with several selected says the first one becomes the cover. Calls go to `POST /api/admin/photos/bulk` in chunks of 200; `failed[]` entries stay selected and are listed under the bar ("1 failed and still selected: photo-1 — Photo not found."), the toast summarises ("2 photos deleted; 1 failed — Photo not found."). **Fallback** on a Worker whose `/bulk` 404s (remembered per page load, probed once): delete loops `DELETE /api/admin/photos/:id`, re-index calls the per-session reindex route and says so ("This Worker can only re-index a whole session, so every photo in it was queued."), one cover uses the existing `PUT` route, move and multi-cover say "needs the new Worker deploy". Tiles get `--tile-aspect: width/height` from the stored dimensions (migration 0012; W2-C's carried request), 4:3 when unknown. The "Photos (n)" count on the card is nudged immediately (a silent dashboard refresh is skipped while the dialog is open / focus is in the grid) and the dashboard refreshes when the dialog closes.
- **Cover-picker step before publish** (`publishSession`, `pickCover`): every publish path (upload flow, retry-publish, the card button) goes through one function. A `409 { needsCover: true }` opens the gallery dialog in `data-mode="cover"` — tiles become one big choice (`.photo-pick`, the existing cover pre-selected), a footer offers "Use this cover and publish" (→ existing `PUT { coverPhotoId }` → publish again) and "Publish without a cover" (→ `{ noCover: true }`); closing the dialog keeps the draft (the card button re-enables; the upload flow says "Draft saved with n photos — it stays private until you pick a cover and publish from Sessions." and, if everything is in, offers a "Publish draft" retry button). An older Worker (no 409) publishes straight away. No new `<dialog>`: the count stays at 4.
- **Session conditions** on create and edit: `breakName, swellFt, wind, tide, photographer, nextDropAt` (a closed `<details>` on the create form, a fieldset in the edit modal; datalists for wind/tide; `conditionsPayload` trims, bounds to the W3-B ranges — 60/30 chars, swell 0–30 one decimal — lowercases wind/tide, converts `datetime-local` → ISO, sends `null` for empties so an edit can clear a value). The edit modal pre-fills from the dashboard's `conditions` + `nextDropAt` and its dirty guard covers the six fields. Cards show a "Conditions · Mulki river mouth · 3.5 ft · offshore · rising tide · by Ankith · next drop Fri, 18 Sept, 07:00" line when present. Older Worker: fields are sent and ignored, nothing shows.
- **EXIF pre-fill** (`readExif`, `exifSuggestion`, `suggestFromExif`): a dependency-free JPEG marker → APP1 `Exif\0\0` → TIFF (II/MM) → IFD0 `Model` 0x0110 / Exif-IFD pointer 0x8769 → `DateTimeOriginal` 0x9003 walker over the first 256 KB of up to 12 JPEGs spread across the pick. The Conditions panel opens with "Shot 06:41–08:05 on 17 Sept with a Canon EOS R6.", the date is set unless the crew typed one (`dataset.typed` from an `input` event; today's default is not "typed"), the camera lands in the photographer **placeholder**. Nothing typed is ever overwritten; a later pick supersedes a read still in flight. HEIC/WebP/PNG are skipped (no EXIF walk for those containers).
- **Indexing observability** on cards (`formatIndexingLine`): "42 queued · 3 running · ETA 7 min · 5 failed" under the progress bar and grouped failure chips ("3 × Face service timed out", biggest first) from the dashboard's `indexing` object; a finished session shows nothing extra (the badge and chips already say it); absent object (older Worker) → today's badge only.
- **Review queue**: a `role="meter"` confidence bar on every pair and link card (0–100, `aria-label="Face similarity 61%"` / "Timing closeness" / "Kit similarity", fill coloured by band: <50 terracotta, 50–74 ochre, 75+ green; all three ≥ 3:1 on the sand track) and a **whole-frame canvas** beside each crop (`renderFullFrame`: the same decoded original the crop came from — no extra request — drawn at the photo's own aspect, ≤ 480 px, with the face box outlined; portrait frames capped at 240 px tall so they never tower over the crop). Only the crop canvases gate the Same / Different buttons.
- **Money tab** (`loadFunnel`, `loadSettlements`): three tiles (searches with "75% found a photo · target 60%", unlocks with "33% of result views · target 25%", rupees with "1 free unlock not counted"), a per-session funnel table (searches → matched → no match → checkouts → unlocks → grants → rupees, rates under the counts, quiet sessions muted, sorted by searches), a settlements table for a date range (default last 30 days from `defaultSettlementRange`, UTR, period, status, amount, total row) and the **unreconciled** payments as buttons that jump to Support with `mj-<paymentId>` filled in and looked up. Missing route → one notice per block ("The funnel needs the new Worker deploy (GET /api/admin/stats)." / "Settlements need the new Worker deploy…"); a 503 (no Cashfree credentials) shows the Worker's line.
- **Support tab** (`runSupportLookup`, `renderSupport`): one box; `detectSupportQuery` reads a phone (with +91 / spaces / dashes), a Cashfree order id (`mj-…` / `order_…`) or a search id and says which as you type ("Looking up a phone"). Results are cards: the search (status chip Paid / Not paid / Free unlock / Expired, session, searched/paid/expiry dates, masked phone, matched / hidden / colour counts, the **"What the guest saw"** thumbnail strip with hidden ones marked, a keyboard-focusable scroller), the payment (order, Cashfree payment id, amounts, refunded so far) and notify-me requests. Actions: **Resend link** (`POST /searches/:id/resend` → the link is shown in the card with its expiry and copied to the clipboard when the browser allows; toast says which), **Free unlock** (reason required, `POST /searches/:id/grant { reason }`, chip flips to "Free unlock", link shown), **Refund** on a captured, not-yet-refunded payment (typed `REFUND` **and** a reason, "Refund ₹700 to the guest? Cashfree returns it to the card or UPI they paid with in 5–7 working days.", `POST /payments/:id/refund { amountPaise, reason }`, toast "Refund of ₹700 requested — Cashfree confirms it by webhook.", chip "Refund pending"). Nothing found → a sentence ("Nothing for the phone ending 3221. Guests only appear here once they reach checkout…"); route missing → one notice.
- **Two new tabs** keep the roving-tabindex keyboard model (arrows / Home / End / wrap; verified by e2e); on phones the five tabs wrap 3 + 2 with the labels still 13 px. **`<main>` landmark** wraps the login card and the studio (W2-B's carried request); the local `--soi-slate-ink` / `--soi-ochre-ink` duplicates are deleted from `admin-theme.css` (W2-A's carried request; `--soi-coral-ink` stays, it has no token). Every new text pair ≥ 4.5:1 (computed in `tests/admin-product.test.mjs`), no rendered text under 11 px on any new screen (harness probe), every new control ≥ 44 px, no horizontal overflow at 375 (harness probe on all eight screens).
- **Cashfree**: no Cashfree code was written or changed here — refunds and settlements are W3-B's routes; this side only calls them and shows their answers. The refund confirm copy is the crew-facing wording; the unmet validation/go-live list is W3-B's (their handoff).
