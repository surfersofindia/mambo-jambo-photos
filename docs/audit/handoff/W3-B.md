## Tasks done (by id)

The block has no F-numbers; ids are the master prompt's bullets.

- **Migration 0014 · session conditions.** `ALTER TABLE sessions ADD COLUMN` × 6. `validateConditions()`: `breakName` ≤ 60, `swellFt` 0–30 rounded to one decimal, `wind`/`tide` ≤ 30 chars (the known words `offshore|onshore|cross|glassy|light|strong` and `low|mid|high|rising|dropping` are stored lower-case, anything else as typed), `photographer` ≤ 60, `nextDropAt` an ISO string in the future or null; `null`/`''` clears a field; each failure is a 400 with its own message. `POST /api/admin/sessions` inserts only the non-empty fields (so a studio that always sends the six keys works on an unmigrated database as long as they are empty; a real value before 0014 → 503 naming the migration). `PUT` does a plain `SET` of exactly the fields sent (COALESCE would not clear). Dashboard session objects and `GET /api/sessions` carry `conditions` (`null` when every field is empty) and `nextDropAt` (`null` unless still ahead); `/api/sessions` also has a top-level `nextDropAt` = the earliest of those. The raw columns never appear in responses. The cover behaviour (`variant=original`, 6-hour token) is untouched.
- **Migration 0015 · support tables.** `match_hides (id, search_id → searches CASCADE, photo_id, similarity REAL NULL, created_at)`, `notify_requests (id, search_id UNIQUE → searches CASCADE, session_id → sessions CASCADE, phone, created_at, notified_at)`, `refunds (id, payment_id → payments CASCADE, cashfree_refund_id, amount_paise, status, reason, created_at, updated_at)`, `grants (id, search_id → searches CASCADE, reason, created_at)`, `searches.colour_photo_ids_json`, `searches.gallery_link_expires_at`, `payments.customer_phone`. **Deviation:** `payments.status` has a CHECK (`created|verified|captured|failed`), so the brief's "payments row with status 'granted'" became the `grants` table, exactly as the lead's note anticipated. **Addition:** `payments.customer_phone` — `payments` stored no phone at all, so a lookup by phone was impossible; the checkout phone (already sent to Cashfree as `customer_phone`) is now kept once the column exists and masked in every response. `gallery_link_expires_at` exists because the 30-day token was never stored, so support could not answer "when does their link expire"; `/access`, `/resend` and `/grant` all write it.
- **`POST /api/searches/:id/colour`** `{ token, hue: 0–359, tone: 'vivid'|'muted'|'any' }` (token in the body, `searchPayload()` shared with `requireSearch()`). The histogram in `photo_appearances` is OpenCV `calcHist` over HSV with 30 hue bins (OpenCV hue 0–180 → 12° each) × 32 saturation bins, row-major, min-max normalised (read from `face-api/main.py clothing_histogram()`). Score = the share of a photo's clothing mass in the chosen hue (exact bin 1, ±1 bin 0.5, ±2 bins 0.15, wrapping around the wheel), with the tone choosing saturation bins (`vivid`: sat bin ≥ 16 full, 8–15 at 0.4; `muted`: 3–15 full, 16–23 at 0.4; `any`: everything except the near-grey bins 0–2 whose hue is noise). Candidates: the session's `indexing_status = 'completed'` photos with an appearance row, minus the search's hidden photos; floor 5 %, top 40, `score` as an integer percent like `/api/match`. Only live unpaid searches (`status = 'preview' AND expires_at > now`, else 410). Quota `limiter(env, 'colour:10m:' + ip, 8, 600)` → 429 + `retry-after` + the search copy, then the opportunistic sweep. The ranked ids replace `searches.colour_photo_ids_json` (the latest colour view is what the guest sees and pays for); before 0015 the results are still returned with a `console.warn` and are not persisted. `previewPayload`/`accessPayload`/`/download` now use `searchPhotoIds()` = matched ∪ colour, de-duplicated. Response: `{ searchId, token, previews, count, pricePaise, currency, indexingNote, session, mode: 'colour', hue, tone }` (`hue`/`tone` are echoed additions). **No funnel event** (the `events` CHECK has no colour kind; not rebuilt) — see "Cut".
- **`POST /api/searches/:id/hide`** `{ token, photoId, score? }` → `{ ok: true, remaining }`. The id leaves `matched_photo_ids_json` and the colour list (one UPDATE), then a `match_hides` row is inserted (`similarity` = `score/100` when the client sends the percent it showed, else null); the insert failing on a missing table only warns, so the photo still leaves the pack. 404 for a photo not in either list (including one already hidden), 410 once the search is paid or expired. `match_feedback` is not written: its `source` CHECK has no guest kind (not rebuilt).
- **`POST /api/searches/:id/notify`** `{ token, phone }` → `{ ok: true }`; phone validated like checkout (`^[6-9]\d{9}$`); `INSERT … ON CONFLICT(search_id) DO UPDATE SET phone, created_at, notified_at = NULL`; 503 "Notifications are not available yet." before 0015 (W3-A's 404 fallback copy also fits a 503).
- **Publish requires a cover or `noCover: true`.** `POST /api/admin/sessions/:id/publish` reads an optional JSON body (none is sent by the session card and the upload flow today); with migration 0009 present, no `cover_photo_id` and no `noCover === true` → `409 { error: 'Pick a cover photo or publish without one.', needsCover: true }`; unknown session → 404 (new); a malformed body → 400. `PUT … { status: 'published' }` is **not** gated (only the publish route is in the contract; both studio paths use `/publish`, checked in `admin.js`).
- **`POST /api/admin/photos/bulk`** `{ action, photoIds, targetSessionId? }` → `{ ok: true, affected, failed: [{ photoId, error }] }`, 1–200 ids, de-duplicated. `delete`: R2 originals/previews/thumbs then `faces` + `photos` per photo (FK cascades take links, pairs, appearances, jobs; a deleted cover clears itself via `ON DELETE SET NULL`). `reindex`: `enqueuePhotos([photo], { force: true })` per photo so the failed ones are named. `move`: `photos.session_id` for those not already there; `photo_links` and `face_verifications` whose **both** photos move follow (session_id updated), pairs split by the move are deleted (a pair only means something inside one session); the source session's cover is cleared if it moved; R2 keys keep the old session id in their path (opaque, still valid); 404 unknown target, 409 archived target. `cover`: the first id becomes the cover of its own session (503 before 0009).
- **Dashboard `indexing`.** One aggregate over `indexing_jobs JOIN photos` per dashboard call (`GROUP BY session, status, error`) → `queued`, `processing`, `done`, `failed`, `failures: [{ reason, count }]` (sorted by count). ETA only for sessions with remaining jobs: a window-function query takes the last 20 completions per session; `etaSeconds` = remaining × the median gap between consecutive completions (≥ 1 s), `null` with fewer than two completions. **Deviation:** the brief says "median duration of the last 20 completed jobs", but `indexing_jobs` carries only `updated_at` (no start time), so inter-completion gaps stand in for duration — with three-way concurrency that is the throughput figure an ETA needs anyway. Best effort (warn + zeros on failure). `stats` are not duplicated on the dashboard.
- **`GET /api/admin/lookup`** — exactly one of `phone` (10 digits) / `order` / `search`, else 400. Phone finds searches through `payments.customer_phone` and `notify_requests.phone`; order through `payments.cashfree_order_id`. Response `{ searches: [{ id, sessionId, sessionTitle, createdAt, status, matchedCount, hiddenCount, colourCount, paidAt, expiresAt, galleryLinkExpiresAt, photos: { matched, colour, hidden } }], payments: [{ id, searchId, orderId, cfPaymentId, amountPaise, status, createdAt, paidAt, phone (masked `98xxxxxx10`), refundedPaise, refundStatus, refunds: [...] }], notify: [{ searchId, createdAt, notifiedAt }] }` — `photos.*` entries are `{ photoId, thumbUrl }` with 15-minute signed thumb (or preview) tokens; grants appear in `payments` as `{ status: 'granted', amountPaise: 0, orderId: null, reason }` rows so the studio shows one timeline; `refundedPaise` excludes `CANCELLED`/`FAILED`. Never a selfie, embedding or unmasked phone. Before 0015 it answers from what exists with `unmigrated: true`. Up to 50 searches.
- **`POST /api/admin/searches/:id/resend`** → `{ link, expiresAt }` for a paid search (402 unpaid, 404 unknown): a fresh 30-day token (the same `/access` mints) as `<site>/?gallery=<searchId>&token=<token>` — site = the caller's allowed Origin, else the first `ALLOWED_ORIGIN`. **The guest page does not read that URL yet** — request to W3-A below.
- **`POST /api/admin/searches/:id/grant`** `{ reason }` (required, ≤ 200) → `{ ok: true, link, expiresAt }`: one batch inserts the `grants` row and sets the search `paid` (rolled back together; 503 before 0015); 409 if already unlocked; no `payments` row, no `paid` event. `/api/admin/stats` gains `grants` per session and in totals (separate query in try/catch so a missing table never blanks the funnel); `unlocks` and `rupees` are untouched by grants. `TODO(wave 4)` comments mark where the crew account goes.
- **`POST /api/admin/payments/:id/refund`** `{ amountPaise?, reason }` — per `.claude/skills/pg/refunds/SKILL.md`: `POST /pg/orders/{order_id}/refunds` with `x-api-version: 2025-01-01`, `refund_id` = our `rf-<uuid>` (unique per order, so a retry can never create a second refund), `refund_amount` in rupees (2 dp), `refund_note`, `refund_speed: 'STANDARD'`. Guards in order: reason required → 503 without credentials → 404 unknown payment → 409 unless `verified`/`captured` → 503 before 0015 → 400 if fully refunded → default amount = what is left, cap enforced server-side. The row is inserted `PENDING` **before** the call; a non-2xx or a network failure marks it `FAILED` and answers 502 (the webhook corrects it if Cashfree had in fact accepted); success stores `cf_refund_id` and `refund_status`. Response `{ ok: true, refund: { id, paymentId, cashfreeRefundId, amountPaise, status, reason, createdAt, updatedAt } }`. Control flow keys off HTTP status and the `refund_status` enum only (`PENDING|SUCCESS|CANCELLED|ONHOLD|FAILED`).
- **`REFUND_STATUS_WEBHOOK`** in the existing `/api/payment/webhook` route, after the same signature + 5-minute freshness checks: `UPDATE refunds SET status, cashfree_refund_id WHERE id = refund_id` (numeric ids arrive as numbers and are stringified); when no row matches and the `order_id` is one of our payments, the refund is inserted (`reason: 'Recorded from the Cashfree refund webhook'`) so dashboard-issued refunds reach the ledger; unknown statuses ignored; re-deliveries set the same status again; nothing here can fail the 200. `SETTLEMENT_*` webhooks are acknowledged and ignored as before.
- **`GET /api/admin/settlements?from=&to=`** — per `.claude/skills/settlements-and-reconciliation/SKILL.md`: `POST /pg/settlements` with `{ pagination: { limit: 100, cursor }, filters: { start_date: '<from>T00:00:00+05:30', end_date: '<to>T23:59:59+05:30' } }`, cursor followed (≤ 10 pages), a bare array or `{ data, cursor }` both accepted → `settlements: [{ id, utr, amountPaise (amount_settled), grossPaise (amount), settledAt, from (payment_from ∥ payment_time), to (payment_till ∥ settlement_time), status, type }]`; then `POST /pg/settlement/recon` (limit 1000) over `from … to + 7 days` collecting the `order_id` of every `PAYMENT` event; `unreconciled` = our `verified`/`captured` payments whose `paid_at` falls in the IST range (UTC `paid_at` shifted by 330 minutes) and whose order no PAYMENT recon event names. Defaults: `to` = today (IST), `from` = 30 days earlier; 400 on a bad range; 503 without credentials; 502 when Cashfree refuses the list; recon failing degrades to `unreconciled: []` with `reconUnavailable: true`.
- **Edge caching.** `/api/media/:id` with a valid token: `preview`/`thumb` → `cache-control: public, max-age=N` where `N = min(3600, seconds until payload.exp)` (a 45-minute preview token gives ≤ 2700; one about to expire gives its remaining seconds; an expired token is 401, never served); plus, when `caches.default` exists (Workers runtime, not Node), `cache.match(request)` after the token check and `cache.put` in `ctx.waitUntil`. The token is in the query string, so the URL is the cache key; `Vary: Origin` from `cors()` is left as is (previews are loaded by `<img>` without `crossorigin`, so a cached ACAO for another origin is harmless). Originals (and `?download=1`) stay `private, max-age=600`. The ZIP stays `no-store`.
