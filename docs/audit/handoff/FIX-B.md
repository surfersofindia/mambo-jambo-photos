## Tasks done (by id)

1. **IPv6 /64 quota key.** `quotaKeyFor(ip)` in the "Per-client quotas" block: trims, strips `[…]` and a `%zone`, lower-cases; IPv4 (octets 0–255) returned whole; `::ffff:a.b.c.d` → `a.b.c.d`; IPv6 validated (only hex/colons, at most one `::`, 1–4 hex per hextet, exactly 8 hextets or `::` standing for at least one) and reduced to `hhhh:hhhh:hhhh:hhhh::/64`; anything else → `'unknown'`. Used by `/api/match` (`match:10m:<key>`, `match:1d:<key>`) and `/api/searches/:id/colour` (`colour:10m:<key>`). `clientIp()` is untouched and still feeds `login_attempts` and `admin_sessions.ip`. Existing keys for IPv4 guests are byte-identical, so nothing resets on deploy; IPv6 guests start fresh windows under the new key (the old full-address rows are swept within a day).
2. **Daily window not charged on a refused request.** The `/api/match` loop charges `MATCH_LIMITS` in order (10 min, then 1 day) and returns the 429 at the first refusal; the refusing window still counts the attempt (unchanged: retrying while blocked never buys quota in *that* window). `tests/indexing.test.mjs` "the search quota upsert counts within a window…" now asserts `10m: 9, 1d: 8` after the ninth attempt, that a further refused retry leaves the daily count at 8, and `1d: 9` after the ten-minute window rolls; the mock-D1 test in `tests/worker.test.mjs` asserts the same plus five refused retries.
3. **Fail open only for a missing table.** `limiter()`: `isMissingTable(caught)` → the old warning + `{ allowed: true }`; otherwise `console.error('rate limiter failed — refusing the request for now')` + `{ allowed: false, count: 0, retryAfter: 30, unavailable: true }`. Both quota call sites answer `quotaUnavailable()` = 503, `retry-after: 30`, `no-store`, body `{ error: 'Searching is briefly unavailable. Please try again in a moment.' }` (the guest page shows `error` text for any non-OK status, so nothing on the client needs to change; a 503 is deliberately not the 429 "you've searched a lot" copy, which would blame the guest for an outage). `requireAdmin()`: missing table → the old warning + accept; any other error → `console.error('admin_sessions lookup failed — refusing the crew token')` + null → 401. The logout route's own best-effort revoke and the login route's insert keep their warnings (out of the brief).
4. **Webhook body bound + cheap checks first.** Order is now: secret/headers present → `webhookTimestampFresh()` → `boundedBody(request, WEBHOOK_MAX_BYTES = 64 KB)` (`content-length` above the cap or a stream that grows past it → 413 via the existing `RequestError`) → `same(hmacBase64(timestamp + raw), signature)` (constant-time, unchanged) → parse and route. A stale timestamp with a bad signature now reports "outside the accepted window" instead of "Invalid webhook signature" (both 401; no test asserted the old message). Cashfree rules followed (`CLAUDE.md`; `.claude/skills/pg/webhooks/SKILL.md` §Step 3 raw-body HMAC and the validation skill's checklist — status below); no behaviour change for valid deliveries: all seven pre-existing webhook tests pass unchanged.
5. **Cover tokens.** `mediaToken(photoId, variant, env, minutes, claims)` spreads `claims` into the payload; `mediaLink()` passes them through. `/api/sessions` mints the cover with `{ scope: 'cover' }` (still `variant=original`, still 6 hours — that product decision is untouched, as instructed). `accessPayload()` mints the paid originals with `{ searchId: search.id }`. The media route accepts `scope` `media` **or** `cover`, then refuses `download=1` on a `cover` token with 403 `Covers cannot be downloaded.` before the D1/R2 reads, and records the `download` event only when the token carries a `searchId` (with that id — previously the event's `search_id` was always null for per-photo downloads, now it matches the ZIP's). Cover rendering is unchanged (200, inline, `private, max-age=600`), and a cover token cannot be re-pointed at another variant (401, as before).
6. **Gallery link seam.** `galleryLink()` → `${site}/?gallery=${encodeURIComponent(searchId)}.${encodeURIComponent(token)}`; `resend` and `grant` both use it. The guest page splits on the first dot; search ids are UUIDs, so the token's own dot is never first. README already described this exact form.
7. **Lookup seam.** `saw` is built from the same signed thumbs as `photos` (no extra tokens): `photos.matched` (hidden: false), then `photos.colour`, then `photos.hidden` (hidden: true), de-duplicated by `photoId`. `photos` is unchanged.
8. **W3-D request.** `export { burstGroups, imageDimensions, similarity, quotaKeyFor }` (no behaviour change). `tests/accuracy.test.mjs`: the self-test via `execFileSync` (using `fileURLToPath`, not `URL.pathname` — the repo path contains spaces, which `pathname` percent-encodes, so W3-D's snippet as written fails here) asserting `/selftest ok: 8 queries, 16 thresholds, worker\.js \/api\/match agrees/`, plus a check that `scripts/accuracy.mjs`'s `similarity` replica agrees with the exported one on seven vector pairs including the `-1` cases. The self-test takes **~0.14 s** (0.18 s for the whole file), nowhere near the 10 s concern.
